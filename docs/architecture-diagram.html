OpenPlayer — how it works

A pocket music player built on a Raspberry Pi Zero 2 W. No screen, no keyboard: you press physical buttons (or tap a web page) and music comes out of your headphones. Here is everything in between.

The big picture

Think of it like a restaurant: you (buttons, phone) place an order, a waiter (agent) writes it down and drops it in a mailbox, the manager (the brain) decides what to do, and the chef (MPD) actually cooks — plays the song — which goes out through the speaker.

Layered design: input agents (Python) translate events to JSON Lines over a local Unix socket; the C# Service validates and orchestrates; OpenPlayer.Core holds platform‑free rules; OpenPlayer.Mpd adapts to MPD, the single source of truth for playback state.

Follow one button press

What happens in the half‑second after you press Next. Hit the button to watch it travel through the diagram.

  1. You press the Next button A tiny switch closes a circuit on the Pi. GPIO pin pulled LOW; gpiozero/lgpio applies bounce_time so one press = one event.
  2. The Hardware Agent writes a note “Someone pressed Next” — written in a simple, standard format. {"type":"button.pressed","button":"next","sequence":1}\n queued by the callback, sent by sender.py.
  3. The note goes in the mailbox Only programs inside the Pi can use it, so nobody outside can sneak in commands. Unix socket /run/openplayer/hardware.sock, created by systemd (RuntimeDirectory), mode 0660.
  4. The brain decides It checks the note is valid and figures out: “Next means skip to the next song.” IpcMessageParser validates → ButtonCommandHandler → IPlayer.NextAsync(), under a global lock.
  5. The adapter tells MPD It translates the order into the music player's own language. One TCP connection per operation to 127.0.0.1:6600; sends next, expects OK or ACK.
  6. MPD plays the next song The real player picks the next song from your memory card. MPD owns queue, position and volume; decodes MP3/FLAC from its library database.
  7. Music reaches your ears Sound goes through the little USB sound card to your headphones. ALSA output hw:CARD=Device,DEV=0 → USB DAC → 3.5 mm jack.

Asking “what's playing?”

The web page asks the brain every 2 seconds “what's playing right now?”. The brain asks MPD and passes the answer back. The web page never talks to MPD directly — it always goes through the mailbox.

The web agent sends {"type":"player.get_snapshot"} (2 s timeout); the Service replies only to that client:

{"type":"player.snapshot","state":"playing","trackTitle":"Example","trackArtist":"Artist","positionSeconds":42,"durationSeconds":210,"volume":35}
{"type":"error","request":"player.get_snapshot","message":"MPD did not respond within 3000 ms"}

HTTP: GET /api/snapshot → 200 / 502 (Service error) / 503 (unreachable). POST /api/buttons/<name> → 204 / 404 / 503.

The six buttons

ButtonWhat it does
play_pausePlay or pause.
previousMore than 3 s into the song → restart it. Otherwise → previous song.
nextNext song.
volume_up / volume_downVolume ±5, kept between 0 and 100.
menuReserved for the future screen. Does nothing yet.

Why it's built this way

One boss for the music

Only MPD knows what's playing. Nobody keeps a second copy that could disagree.

MPD is the single source of truth for track, queue, state, position and volume.

Buttons never touch the player

Buttons only send notes. Swap the buttons for a phone and nothing else changes.

Agents emit events only; no MPD access. Replaceable inputs share one IPC contract.

Rules live apart from hardware

The “thinking” part can be tested on a normal computer, no Pi needed.

OpenPlayer.Core has no sockets, GPIO, processes or file I/O.

Private by default

The mailbox and player only accept requests from inside the device or your home network.

Socket 0660 + group; MPD on localhost; web agent rejects non‑private IPs with 403.

Gets back up on its own

If a part crashes, it restarts and reconnects without you doing anything.

systemd restarts; agent reconnects with 0.5–10 s backoff; MPD failure only fails that one call.
