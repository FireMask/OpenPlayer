OpenPlayer — how it works

A pocket music player built on a Raspberry Pi Zero 2 W. No screen, no keyboard: you press physical buttons (or tap a web page) and music comes out of your headphones. Here is everything in between.

The big picture

Think of it like a restaurant: you (buttons, phone) place an order, a waiter (agent) writes it down and drops it in a mailbox, the manager (the brain) decides what to do, and the chef (MPD) actually cooks — plays the song — which goes out through the speaker. The manager also has a watcher standing by the kitchen: the moment anything changes, it tells every waiter, so your phone shows it right away.

Layered design: input agents (Python) translate events to JSON Lines over a local Unix socket; the C# Service validates and orchestrates; OpenPlayer.Core holds platform‑free rules; OpenPlayer.Mpd adapts to MPD, the single source of truth for playback state. A watcher in the Service waits on MPD's idle and pushes each new snapshot to subscribed agents; the web agent relays it to browsers over SSE.

Follow one button press

What happens in the half‑second after you press Next. Hit the button to watch it travel through the diagram.

  1. You press the Next button A tiny switch closes a circuit on the Pi. GPIO pin pulled LOW; gpiozero/lgpio applies bounce_time so one press = one event.
  2. The Hardware Agent writes a note “Someone pressed Next” — written in a simple, standard format. {"type":"button.pressed","button":"next","sequence":1}\n queued by the callback, sent by sender.py.
  3. The note goes in the mailbox Only programs inside the Pi can use it, so nobody outside can sneak in commands. Unix socket /run/openplayer/hardware.sock, created by systemd (RuntimeDirectory), mode 0660.
  4. The brain decides It checks the note is valid and figures out: “Next means skip to the next song.” IpcMessageParser validates → ButtonCommandHandler → IPlayer.NextAsync(), under a global lock.
  5. The adapter tells MPD It translates the order into the music player's own language. One TCP connection per operation to 127.0.0.1:6600; sends next, expects OK or ACK.
  6. MPD plays the next song The real player picks the next song. The one you skipped leaves the queue. MPD owns queue, position and volume. With consume 1 the finished or skipped song is removed and the current one stays first.
  7. Music reaches your ears Sound goes through the little USB sound card to your headphones. ALSA output hw:CARD=Device,DEV=0 → USB DAC → 3.5 mm jack.

Watch the page update itself

Right after MPD changes — because of a button, a song ending, another phone or mpc on the Pi — every open web page shows it in well under half a second. Nobody has to ask.

  1. MPD changes something A new song, pause, volume, or someone edited the queue. The watcher's idle player mixer playlist options returns, e.g. changed: player.
  2. The watcher takes a fresh picture It asks MPD “what's playing now?” and, if the song changed, remembers the old one for ⏮. status + currentsong under the global lock; Observe() adds the previous song to the history (last 50) if it played.
  3. It drops the news in the mailbox Every program that asked to be kept informed gets a copy. player.snapshot pushed to each player.subscribe connection, outside the lock, in parallel, 2 s timeout; a stuck subscriber is dropped.
  4. The Web Agent passes it on It keeps the latest news and hands a copy to every open page. Events thread stores latest and puts the line into one queue per page (≤ 8 pages, queue of 16).
  5. Your phone redraws Title, progress bar and queue change on screen. Nothing was polled. GET /api/events sends data: <line>; EventSource.onmessage → show(); a new queueVersion reloads the queue.

How the page stays up to date

When the web agent starts, it tells the brain “keep me informed” and keeps that line open. Each page you open gets the latest news first, then every change as it happens, plus a small “still here” signal every 15 seconds. If the connection drops (phone in your pocket, the brain restarting), the page falls back to asking every 2 seconds until the connection comes back on its own. The web page never talks to MPD directly — it always goes through the mailbox.

Subscription (SPEC 16): a dedicated connection, one message, then only pushes.

→ {"type":"player.subscribe"}
← {"type":"player.snapshot","state":"playing","trackTitle":"Example","trackArtist":"Artist","positionSeconds":42,"durationSeconds":210,"volume":35,"queuePosition":0,"queueVersion":42}
← (one line per MPD change)
← {"type":"error","request":"player.get_snapshot","message":"MPD did not respond within 3000 ms"}

Browser side: GET /api/events → 200 text/event-stream, latest line first, data: <line> per change, : ping every 15 s, 9th page → 503. While the stream is open the page does not poll; on onerror it polls GET /api/snapshot every 2 s. If the Service goes down the web agent sends the error line (page: “Sin conexión con el reproductor”) and resubscribes every 2 s.

Other HTTP: GET /api/snapshot → 200 / 502 / 503. POST /api/buttons/<name> → 204 / 404 / 503. POST /api/seek → 204 / 400 / 503. Library, lists and queue routes → 200 / 204 / 400 / 502 / 503 (see architecture.md §5).

What the web page can do

▶ Player

The six buttons, the current song, and a progress bar you can drag to jump inside the song.

Buttons → button.pressed; progress advances locally between snapshots; release → player.seek (seekcur).

📚 Library

Browse folders, search, play a song, or use “+” to play it next, add it to the queue or to a list.

library.browse / search (pages of 100), library.play, queue.add (next → after the current one).

🗂 Lists

Your saved playlists: create, rename, delete, reorder, remove songs and play from any song.

playlist.* over MPD's stored .m3u files; playlist.play replaces the queue.

🎶 Queue

What plays next, with where each song came from. Jump, reorder, remove, clear or save it as a list. Played songs leave on their own.

queue.* by MPD song id; consume 1; source labels kept in Service memory; reloaded only when queueVersion changes.

⏮ Real “previous”

In the first 3 seconds, ⏮ brings back the song you heard before, even though it already left the queue.

History of the last 50 played (in memory); add URI 0 + play 0 with its source label; past 3 s it restarts the song.

Why it's built this way

One boss for the music

Only MPD knows what's playing. Nobody keeps a second copy that could disagree.

MPD is the single source of truth for track, queue, state, position and volume. The Service only keeps what MPD can't: source labels and the ⏮ history.

Inputs never touch the player

Buttons and the web page only send notes. Swap the buttons for a phone and nothing else changes.

Agents emit events only; no MPD access. Replaceable inputs share one IPC contract.

News is pushed, not polled

Pages don't keep asking “anything new?”. The brain tells them the moment something changes.

One idle watcher in the Service → player.subscribe push → SSE. Polling every 2 s is only the fallback.

Rules live apart from hardware

The “thinking” part can be tested on a normal computer, no Pi needed.

OpenPlayer.Core has no sockets, GPIO, processes or file I/O.

Private by default

The mailbox, the player and the shared folder only accept requests from inside the device or your home network.

Socket 0660 + group; MPD on localhost; web agent rejects non‑private IPs with 403; Samba limited to private networks.

Gets back up on its own

If a part crashes, it restarts and reconnects without you doing anything.

systemd restarts; agents reconnect (hardware 0.5–10 s backoff, web subscription every 2 s); MPD failure only fails that one call.
