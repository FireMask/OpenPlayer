    Los mensajes del buzón
    
  
    Todo lo que entra al socket Unix del Service es una línea JSON. Hay tres formas de conversar. Contrato completo en docs/architecture.md §7.
    
  
    
  
    
    
    FormaMensajesQué vuelve
    
    
    Sin respuesta
    Deja la nota y se va.Conexión por pedido; el log y MPD bastan.    		
      button.pressed · player.seekNada. Si MPD falla, solo un warning en el log.
    
    
    Pide y espera
    Pregunta y espera una línea.Una conexión por pedido; timeout 2 s (snapshot) o 5 s (resto).    		
      player.get_snapshot · library.* · playlist.* · queue.*
      player.snapshot, library.page, playlist.list, queue.page, ok o error. Siempre exactamente una línea.
    
    
    Suscripción
    Pide que le avisen de todo.Conexión dedicada; el Service deja de leerla.    		
      player.subscribeUn player.snapshot enseguida y otro por cada cambio de MPD; la línea error si MPD falla.
    
  
    
  
    

  
    Reglas que no cambian
    
  
    
    
    Solo el Service habla con MPDLos agentes nunca abren el puerto 6600. La excepción es mpc por SSH, que es administración.
    
    
    Un comando a la vezTodo lo que toca MPD pasa por un lock global (_commandLock). Los push salen fuera del lock para que un suscriptor lento no frene los botones.
    
    
    MPD es la verdadCada push es el snapshot completo, no una diferencia. La página siempre puede redibujarse con la última línea.
    
    
    Las líneas tienen límiteHasta 4096 bytes de entrada por línea; más, y se cierra esa conexión. JSON inválido: warning y la conexión sigue.
    
    
    Todo se recupera solosystemd reinicia; el web agent se resuscribe cada 2 s; el observador reintenta MPD cada 5 s; el navegador reconecta el EventSource.
    
    
    Sondeo solo de respaldoCon el stream abierto la página no pregunta. Si se corta, vuelve a GET /api/snapshot cada 2 s hasta reconectar.
